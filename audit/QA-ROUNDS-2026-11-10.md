# SAFI - Correcciones por versiones: validacion local

Fecha: 10 de noviembre de 2026.
Rama: dev/safi-audit-finance-core.
Base: e09de28c1e76274f5f16a1201c1468b553c1db3e.
Alcance: modulo local de evidencias y correcciones, no la plataforma completa.

## Problema resuelto

La revision "needs-more-information" quedaba registrada, pero el trabajador no podia enviar otra respuesta: el servidor solo admitia una respuesta por solicitud y el borrador recibido quedaba bloqueado. Ahora cada nueva respuesta tiene un numero de ronda, identificador y referencia al comprobante anterior.

## Implementacion

- Solo se abre otra ronda cuando la respuesta anterior fue revisada con solicitud de mas informacion. Debe coincidir el comprobante padre y la ronda siguiente.
- Las respuestas anteriores, sus fotos y las revisiones se conservan. El administrador ve primero la version mas reciente y revisa por comprobante exacto.
- Los reintentos, incluidos los de rondas anteriores, recuperan su comprobante sin crear otra version. Datos distintos con la misma identidad se rechazan.
- La copia local anterior se archiva y el nuevo borrador se crea en una transaccion IndexedDB. Se comprueba la version activa dentro de la transaccion; no se sobrescribe un cambio de otra pestana.
- La nueva respuesta permite una nueva fotografia sin reemplazar la original. La interfaz muestra la nueva instruccion y un historial local desplegable.
- Los registros SQLite anteriores sin campos de ronda se interpretan como ronda 1. No se cambia el esquema ni se elimina informacion previa.
- Se corrigio un mensaje de confirmacion que ocultaba errores de guardado y otro que seguia indicando "solo local" despues de recibir confirmacion.
- El servidor y el cliente mantienen los limites y las restricciones de la demostracion. Maximo 100 rondas por la solicitud ficticia.

## Ejecucion verificada

- Base local: 32 pruebas Node aprobadas, 0 fallos.
- Version actual: 44 pruebas Node aprobadas, 0 fallos, 0 omitidas (32 existentes + 12 nuevas).
- Interfaz: 49 comprobaciones aprobadas, 0 fallos (12 trabajador + 13 evidencias + 24 rondas).
- Sintaxis: 14 comprobaciones aprobadas.

Las pruebas nuevas verifican apertura de una segunda ronda, rechazo de estados o referencias incorrectas, reintentos tardios, ocho envios concurrentes identicos, decisiones dirigidas a una version, numeros de ronda invalidos, fotos y comprobantes tras reinicio, compatibilidad con registros anteriores, borradores inmutables, revisiones desactualizadas, perdida de confirmacion y comprobantes de una ronda distinta.

## Alcance de las pruebas

Node.js 22.16.0, HTTP real en 127.0.0.1 y SQLite local con directorios temporales. Se usaron notas ficticias y una imagen PNG de prueba, no datos de trabajadores.

Las pruebas de interfaz ejecutan scripts en Chromium con respuestas HTTP y transacciones IndexedDB simuladas. Verifican botones, estados, archivo atomico simulado, historial y ausencia de desbordamiento horizontal en 320, 390, 768 y 1280 pixeles CSS. Las capturas muestran datos simulados. No certifican IndexedDB real, camara, perdida de conexion de un telefono, Safari, Android ni dispositivos fisicos.

## Reproducir

Desde la raiz del repositorio:

```sh
node --test audit/field-demo-server.test.mjs audit/field-correction-client.test.mjs audit/field-evidence-store.test.mjs audit/field-correction-rounds.test.mjs
python audit/qa/worker-corrections-ui.py
python audit/qa/evidence-review-ui.py
python audit/qa/correction-rounds-ui.py
```

Las comprobaciones visuales necesitan Playwright y Chromium ya instalados. El servidor no incorpora dependencias nuevas. El workflow existente descubre los nuevos archivos .test.mjs; los resultados aqui descritos son locales, no una afirmacion sobre el resultado de CI del nuevo commit.

## Limites pendientes

La solicitud y los usuarios siguen siendo ficticios. Falta integrar solicitudes dinamicas, autenticacion, permisos de servidor, cifrado, copias de seguridad y los demas modulos. El servidor sigue limitado al propio equipo. No habilitar acceso desde Wi-Fi o internet ni introducir informacion real. Las comprobaciones de cabecera de imagen no equivalen a decodificacion completa ni escaneo de seguridad. El historial preservado por la aplicacion no es inalterable frente a quien controla la base de datos.

No se modificaron main, el sitio publicado, Firebase, cuentas, credenciales ni datos reales. No se activaron servicios externos facturables.

## Reversion

Revertir este cambio en la rama de desarrollo. La base anterior no entiende las rondas nuevas: conservar una copia del almacenamiento de prueba y usar un directorio separado al evaluar una version antigua. No eliminar bases de datos ni restablecer main.
